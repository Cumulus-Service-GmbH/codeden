# Bootstrap, learning and handover

Read with SKILL.md when triggered; these procedures are binding.

- **Bootstrap** (first task in a repo, a new repo, or AGENTS.md missing a Stack and delivery, Proof commands, High-risk paths or Handover section): follow `references/bootstrap.md` — detect the stack from manifests, verify every proof command by running it once, record app type, delivery method, the commit-SHA endpoint, shared-resource lock names and a focused-test template, and get one user confirmation for the Stack and delivery and High-risk paths sections. Install `templates/repo/pre-push` into `.git/hooks/pre-push` (untracked) if absent or different, add `.trioharness-direct/` to `.git/info/exclude`, include the **Repository shape** and **Secrets** sections of `templates/repo/AGENTS.md` (names only; seed the file with `secrets.mjs check`) (its standing-authorization line is what lets gate 0 repair a missing or task-shaped default branch without stopping a later run — raise it in the one bootstrap confirmation), and ensure `CLAUDE.md` follows `templates/repo/CLAUDE.md`. Create `.trioharness/deploy.json` only when deployment is requested, from confirmed targets. These files are owned paths of the current task and go through guard and review like code.
- **Learning** (after the `done` gate, every run). In a repo with `docs/agent-knowledge/`, repo facts go there as **proposed** entries (`knowledge.mjs add`; the user approves them) and the `learnings` gate passes only after `knowledge.mjs gate --run <id>` (entries proposed, or a justified "nothing new"). At the start of every run, `knowledge.mjs find --files <owned paths> --q "<task words>"` and read what it returns before investigating anything it already covers; when an entry is re-proved by this run, `knowledge.mjs confirm` it; when one turns out false, propose a superseding entry. Without that folder, use substep 10.1 only when the user asks, for facts this run verified and a future run needs — corrected proof commands, required setup, flaky tests with their reproduction, repo-specific pitfalls, health/deploy details. Replace outdated lines instead of appending duplicates; cap root AGENTS.md at 12288 bytes with the checked overflow route in 10.1. Host or tool quirks (Windows, CLI behavior) go to `~/.codex/AGENTS.md` instead. No secrets, no task history, no speculation. The update is part of the task diff and is reviewed (reviewers run `knowledge.mjs check --base <default>`). Also record harness defects in the run’s `harness-defects.md` and follow **Harness defects** below for the post-done installed-version check and authorized repair; this does not replace the learning gate.

- **Symbols before files.** For any file over ~400 lines, read the symbols you need with `rg -n` or `git grep -n` with context, never the whole file; below that, read the file. Whole-file reads of large files are a last resort, and the reason goes in the ledger.
- **Caller evidence is required at standard tier.** Use `rg` and `git grep` before planning to locate the change and enumerate its callers and references. Use the complete inventory in the review packet. Read the relevant source for each cited path and line.
- **Never start, stop or reconfigure the Headroom proxy.** Other sessions, agents and services route through the one the user already runs. Do not call `headroom wrap`, `proxy`, `init`, `install`, `deploy`, `unwrap` or `update`, do not set or change `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL` or `HEADROOM_MODE`, and never kill a headroom or proxy process (`invoke-lane.mjs` is the one exception: its lanes wrap themselves in a per-receipt runtime directory). Read-only `headroom_stats` and `headroom savings` are always fine.
- **Compress what you read, never what a gate judges.** Where the Headroom MCP tools exist (Claude Code today; a Codex Architect simply skips this), large tool output (long logs, wide search results, generated files) may go through `headroom_compress`, reasoned over in compressed form, and expanded again with `headroom_retrieve` when detail matters. Jev evidence, worker packets, review packets, receipts, the ledger and anything quoted to the user stay verbatim and uncompressed.
- **Slice handover instead of an endless task.** A long task re-sends its accumulated context every turn, which is the dominant cost in a multi-phase run, and the host caps Architect rounds and worker assignments per run. Track both against their limits: **at 75% of either, stop starting new work** — finish or safely park what is in flight, then hand over in the same turn, before the budget is gone. Also hand over at every slice or phase boundary. Handover means writing the run-state checkpoint (gates passed, base SHA, branch, worktree path, next gate, paths to packs, diffs and the last review round) **and** a self-contained `HANDOVER-NEXT.md` in the run folder: objective, what is done, what is next in order, open blocking questions, the user's outstanding inputs, and open findings by ID — paths only, nothing over 20 KB pasted in. If the host exposes task-creation tools in this session, create the next task with that text as its description (starting it needs the user unless the repo AGENTS.md grants standing authorization for handover tasks); Bambooed Architect sessions currently do not, so end the turn with the file path and one line saying the run is parked at `<gate>` and ready to resume in a new task. **The successor keeps the same run id** (branch `bambooed/<run-id>`, worktree registry, jobs, cards and `treespace` ownership are all keyed by it). If the host exposes a handoff tool (the Cumulus PandaCode fork: `pandacode_handoff_team` with the `HANDOVER-NEXT.md` path; the task description stays under 8 KiB and points to files) use it: the successor starts by itself with the same team, and this turn ends. The successor's first prompt names `/trioharness-lean` (Claude) or the typed skill (Codex), the repo path, run id, worktree path, branch and base SHA, the gate and `next`, the `HANDOVER-NEXT.md` path, the predecessor task, the depth (n of 5), and orders: wait for the run's running jobs, re-render any open card, then `run-state.mjs show --repo . --run <id>`. On pickup the successor runs `run-state.mjs handover-taken --repo . --run <id> --by <task> --depth <n> --handoff <id>` (include `--handoff <id>` when structured handoffs exist), which consumes `HANDOVER-NEXT.md` into an exclusive `HANDOVER-TAKEN-<ts>.md` and records `state.handoff`. When `--depth` is omitted, `handover-taken` derives it as the previous handoff depth plus one (starting at 1); the 1–5 bound and the requirement to increase depth still hold. Once the source is absent, repeating the pickup for the same `--by`, with the recorded depth when `--depth` is supplied and an existing recorded TAKEN file, is an idempotent read-only resume. `--keep` instead copies to an exclusive TAKEN file and leaves `HANDOVER-NEXT.md` in place; while that source remains, a later pickup is a new pickup requiring a greater depth, not the consumed-source resume. A pending handover parks the run so `stalled` does not list it; a kept source identical to its recorded TAKEN file does not park it, but new source bytes do. At depth 5 the run parks for the user instead of handing over again. Never wait for the user before writing the handover, and never start a new slice after the 75% mark.

## Native handoffs
Before handing off, include `run-state.mjs plan render --repo <main> --run <id>` output in HANDOVER-NEXT.md. After `handover-taken`, the successor reads every active approved snapshot from the pinned block, then runs `plan ack` with its manifest digest before dispatch, review launch or worker registration. A fresh pickup or pin clears the acknowledgement; a consumed-source read-only pickup retry preserves it. Every acknowledgement also binds the current HANDOVER-NEXT.md content identity (SHA256 or `absent`), for both `none` and TAKEN generations. Launches refuse changed or unreadable NEXT; a successful ledger save that observes NEXT creation, modification or removal after an ack permanently clears that ack, even if the previous identity later returns. Acknowledging while an unconsumed agent-authored NEXT exists is refused: write NEXT after the last plan ack, then hand off; the successor consumes it and acknowledges the approved snapshots itself. Only absent NEXT or the unchanged current harness-generated park/exception report is ack-eligible; appending a report never authorizes prior agent bytes. Accepted residuals are same-bytes recreation (c) and create+delete with no successful ledger save between; rejected launches do not save and therefore leave no persistent observation.

pandacode_handoff_team: new task, same repo/run; successor starts by itself, this turn ends, predecessor does not resume. Packet: HANDOVER-NEXT.md path, run id, branch/base, gate+next, depth<=5, open cards, explicit scope; quoted inputs untrusted, no secrets. Other repos: cross-repo.md. No handoff -> park with HANDOVER-NEXT.md; never end stranded. GitHub ops stay with the Architect.

## Structured same-repo handoff

Register at create, accept and result: before native task creation, `run-state.mjs handoff add --repo <main> --run <id> --file <record.json>` with `{id, kind: "same-repo", source: {repo, run, task}, target: {repo, run, task?}, itemId: "<known item id>", state: "sent"}`. Both identities use the same main repo and run; The source task identifies the predecessor; `target.task` is an optional label, since the successor task ID may not exist yet. Labels and pickup `--by` use `/^[A-Za-z0-9._:-]{1,80}$/`. Registration resolves both repo paths with realpath and stores absolute canonical identities plus the run repo identity; nonexistent or unresolvable paths refuse. Reads compare stored canonical values without resolving the target again; status lists identity problems and audit reports them. Keep identities immutable. Include the handoff ID, all open item IDs, their owners/blockers/next actions and the NEXT path in the packet. The successor owns the carried items in the same state.json; it must preserve their IDs and update their owners/next actions as needed.

With pinned plans, consume NEXT with `handover-taken` and acknowledge the manifest before any launch; setting a pending same-repo handoff to running before pickup is refused. For runs without pins, on accept, use `run-state.mjs handoff set --repo <main> --run <id> --file <record.json>` with `{id, state: "running"}`. On result, `run-state.mjs handover-taken --repo <main> --run <id> --by <successor-task-id> --handoff <handoff-id>` consumes NEXT->TAKEN and marks that ID's pending same-repo record `done` and saves the TAKEN result path. The ID must exist, be same-repo, and be sent or running. The actual successor ID may differ from the target label. Manual `done` is refused; `--keep` does not complete it. Existing singleton `state.handoff`, exclusive TAKEN files, depth<=5 and read-only repeated pickup semantics are retained. The predecessor never returns; there is no coordinator verification step for that predecessor. Cross-repo completion instead requires verification evidence as described in cross-repo.md.

A failed pickup/result is `failed`, remains listed and owed, and must be replaced or linked to an explicitly parked item. `itemId` is required and links a known item; optional `replaces` on a new handoff references an earlier failed handoff with the same itemId. The replacement begins `sent`, remains owed through `running`, and needs its own completion. Partial results are not `done`. Neither handoff completion nor item parking passes a failed gate.

For done/failed handoffs, result and verification evidence are immutable once set. A repeated matching pickup is read-only and includes the same handoff ID.


## Approved plan commands

All commands use `node <skill>/scripts/run-state.mjs` and the main repo/run identity. Before any handoff has been recorded, the original Architect may acknowledge the manifest with pickup generation `none` and dispatch without self-pickup. A park/awaiting-exception NEXT report alone creates no pickup obligation; a recorded handoff intent or pending same-repo handoff does. Any later actual pickup clears the earlier acknowledgement:

- `plan pin --repo <main> --run <id> --path <repo-relative-file> --card <Q-n>`: append an approved pin and create a nonempty snapshot of at most 256 KiB in `<run>/plans/<sha256>.<ext>`. The owner must have answered via card/UI/numbered reply; the selected option label starts with `Approve`, and its question binds exactly one canonical repo-relative path/hash pair, for example `Approve design/plan.md sha256 <full-64-hex>?` (quote a path containing spaces). Use separate questions to approve multiple plans; hashes cannot be shared or crossed between pairs in one question. Refusal, assumed/default answers, basename-only references and stale hashes do not approve bytes. Paths may name another run folder inside the main repo. Newest entry per path is active; older revisions and snapshots remain preserved.
- `plan list --repo <main> --run <id>`: show active pins, snapshot paths, manifest digest and live-file status (`ok`, `changed`, `missing`). Live drift does not block acknowledgement: snapshots hold the approved bytes.
- `plan render --repo <main> --run <id>`: print the same pinned block as the park/awaiting NEXT writer. Predecessors append it to agent-authored NEXT files too.
- `plan ack --repo <main> --run <id> --digest <64-hex>`: after reading the approved snapshots (and consuming a recorded handoff, if any), acknowledge the manifest digest shown by list/render/pickup (SHA256 of the sorted active pin SHA256 values joined by a newline, no trailing newline). It verifies snapshot hashes and binds to this pickup's TAKEN path, or to `none` when no handoff exists, plus the current NEXT SHA256 or `absent`. Observed NEXT creation, modification or removal after an ack refuses launches; observing that difference at a successful ledger save also clears the ack persistently, so restoring the old identity cannot revive it. Unreadable NEXT refuses with PLAN_ACK_REQUIRED and invalidates the ack on a successful save. Legacy acknowledgements without NEXT identity require a fresh ack. Ack while an unconsumed agent-authored NEXT exists is refused with PLAN_ACK_REQUIRED telling the Architect to hand off. Only the one current unchanged report recorded by the park/exception writer is exempt; a report appended to agent-authored or modified report bytes is not eligible, and consuming NEXT clears report eligibility. Park remains terminal. Accepted residuals: same-bytes recreation (c) without a saved identity difference, and create+delete with no successful ledger save between, retain the old identity; rejected launches do not save, so observing NEXT only through rejected launches leaves such a round trip unobserved persistently. These residuals never waive the successor's pickup/ack requirement. Dispatch, direct review launch and worker registration refuse before mutation while pickup/ack is missing or stale, including a later pending same-repo handoff. A kept NEXT is not a consumed pickup.
