# Jobs, run state and blocking questions

Read with SKILL.md when triggered; these procedures are binding.

<!-- Baseline SKILL.md lines 48-49 -->

- **Turn discipline (Bambooed resumes the Architect only when a dispatched worker returns):** end a turn to wait only on registered workers or host-supported registered job survivors, with open items listed; otherwise finish/stop only for an allowed reason. Never end a turn while waiting on an unregistered shell job, an unsupported background survivor, or an unregistered file producer: nothing wakes you when it ends, so "I'll continue when it returns" strands the run until the user types. Run tests, builds, Playwright and every other long command through `node "<skill>/scripts/jobs.mjs" run --repo . --run <id> --name <job> --cmd "<command>" --timeout <sec>` (foreground, hard timeout of 540 s by default, whole process tree killed, exit code kept); for a job longer than one tool call, `jobs.mjs start` it and then `jobs.mjs wait` for it inside the same turn unless the host guarantees registered-job survival and run resumption, repeating `wait` only while it exits 124 (still running; 125 = supervisor lost, 126 = the job hit its timeout). Before ending ANY turn run `jobs.mjs check --repo . --run <id>`: exit 2 means a job is unresolved and the turn must not end except for that host-supported registered-job wait with items listed (`questions.mjs check` exit 2 is the opposite: a card is open and the turn MUST end now, with nothing else started). `run-state.mjs finish` and the `learnings` gate refuse while a job is unresolved. Heavy jobs (Playwright shards, emulator or SDK downloads, full test suites, reviewers' test runs) add `--heavy`: they share two machine-wide slots (`--slots`, `THL_HEAVY_SLOTS`), so they queue instead of starving each other and the workers (`queued` counts as unresolved for `check` and `wait`; `stop` ends a queued job without running it); `run --heavy` defaults to a 60 s slot wait and a 480 s timeout and keeps both within 570 s, so use `start` + `wait` for anything longer; no slot in time gives status `no-slot` and exit 75 and runs nothing. Every `jobs.mjs` call is made with the host's explicit tool timeout set above the call's own limit (Claude Bash `timeout` 600000 ms; Codex `timeout_ms` the same): a host that kills the shell call at its default (120 s) kills the wait, and a SIGKILL leaves the job running orphaned and recorded `lost`. A `lost` job whose supervisor died may still be running: `jobs.mjs stop --lost` stops it by pid only when the pid still shows the job's command line; never rerun it under the same name before that. On Windows the host ends every process of a turn when the turn ends, so a `start`ed job lives only inside the turn that waits for it: `start` + `wait` in one turn is fine, anything meant to outlive a turn is not. Ask a question card only after the run's jobs have settled (`questions.mjs ask` refuses with JOBS_OPEN): a card ends the turn and a running job forbids ending for a question card. Dispatch every worker with `run-state.mjs dispatch --run <id> --role <role> --worker <id> --deadline-min <n>` (default 30) and close it with `worker-done --status done|failed|stopped`. A worker you see stopped or killed in the app, or that is silent past its deadline (`stalled` reports those), counts as FAILED: nothing resumes you for it, so take over at once (verify its edit yourself or redo it) — but first cancel it with the host's cancel-worker tool so it stops editing the shared checkout, and `jobs.mjs stop` any job it started. Begin every resumed turn with `run-state.mjs stalled --repo .`: exit 2 lists runs with open work, nothing running and no sign of life, plus overdue workers, lost jobs and unreadable state at once; a parked run with `HANDOVER-NEXT.md` is not listed. It is a signal, not authority: a run you did not start in this task may belong to another live session, so report it to the user instead of taking it over. Before ending a turn to wait on workers, write the resume point with `run-state.mjs`. On successor pickup, `handover-taken` derives depth from the previous handoff plus one when `--depth` is omitted; after the source has been consumed, a matching pickup is an idempotent read-only resume. `--keep` leaves `HANDOVER-NEXT.md` in place (see Slice handover for the precise resume conditions). Four endings are never allowed while work is still owed: a summary that announces the next step instead of taking it; an offer to carry on unless the user prefers otherwise; a list of decisions for the user when none of them blocks the remaining work; and stopping because the turn has been long or a milestone is done. Status notes and recommendations are welcome — put them in the same message as the next action and carry on with whatever does not depend on the user's answer. The stops that are allowed are the ones where nothing can move without the user, where the blocker is deliberately protected (production authorization, an unmerged PR), or where a gate forbids proceeding.
- **Asking the user: question cards only, and the run stops.** Every question is first classified: **blocking** (the next step cannot be taken or would be a guess — a missing credential or endpoint, an ambiguous acceptance criterion, a scope or design decision, an authorization, a choice between incompatible options) or **non-blocking** (a preference, a nice-to-have, something with a safe default). A non-blocking question is a note carried in the same message as the next action, and work continues. A blocking question is asked ONLY as a **question card**: 1–4 questions, each with 2–4 fixed options, one recommended option and a one-line reason; no free-text field, no open-ended question in prose. Write the card to a file, then `node "<skill>/scripts/questions.mjs" ask --repo . --run <id> --file <card.json>`; it validates the card, records it open, and prints the card in host form. Show it with the host's question-card tool (PandaCode renders cards; Codex `request_user_input` with `isOther:false`; Claude `AskUserQuestion`) — a host with no card tool gets `questions.mjs render` (numbered options; the reply must be option numbers). Then record the gate `blocked` and END THE TURN: while a card is open, `run-state.mjs` refuses every gate advance, every dispatch and `finish`, and `questions.mjs check` exits 2. Never ask and continue, never act on an assumed answer, never turn a reply that is not one of the card's options into an answer (ask again with a better card). The answer is recorded with `questions.mjs answer --run <id> --set Q-<n> --answers '{"q1":"a"}' --via card|ui|numbered-reply --quote "<verbatim>"` (option ids plus the verbatim user selection as provenance) and the run resumes at the recorded gate. Several open blocking questions go on one card (at most four); workers never ask the user — they write `QUESTIONS NEEDED` in their result file and the Architect puts them on a card. Details, the card format and the interview method: `references/questions-and-knowledge.md`.
- **Fewer cards:** Safe defaults never override a card, authorization or scope boundary another rule requires (production/deploys, db-ops reads/writes/changed scripts, secrets, merge/install/adopt, gate/scope questions, design-system, dependency/API/schema changes) nor blocking stops, no ask-and-continue or owner exceptions. Cards for the cases above; do not ask these: confirmations after fix/go/proceed; per-repo/per-step choices, ordering, test-first, retries or naming. Otherwise Architect takes safe default, states it in one line in next report, continues; never re-ask approved sub-steps within the same approved step. Batch unavoidable questions in one card (<=4).
- **Status block:** At each gate or packet checkpoint and end of every turn, Architect's report ends with a status block derived from plan/ledger/run-state (facts only, no new claims, <=12 lines): Done (finished plan steps, merged PRs); Now (current step); Next (next step); After that (remaining plan steps in order); 'Round n of N' only when the host supplies it; omit lines with nothing to report. The skill cannot push updates between turns.

## Structured scope and owed work

At gate 3 use `run-state.mjs scope --repo <main> --run <id> --file <scope.json>` with `{outcome, nonGoals: [], files: []}`. The baseline is set once and immutable. An expansion requires an owner card and revised approved plan, never an implicit file-list edit. Record out-of-scope work with `run-state.mjs defer --repo <main> --run <id> --file <record.json>`: `{id, item, reason}` is append-only; duplicate IDs refuse.

Use `run-state.mjs item add|set --repo <main> --run <id> --file <record.json>` for `{id, item, owner, status, blocker, next, reason?}`. `add` requires a new ID and full record; `set` merges a partial record by existing ID. Status is `open|blocked|done|parked`; open|blocked needs owner and next action; blocked also requires a nonempty blocker. Parking requires an explicit reason, next owner in `owner`, and next action in `next`. A parked item stays listed; it does not satisfy accepted-done criteria or delivery gates. Set can also use `--id`, `--status`, `--owner`, `--next`, `--blocker`, `--reason` instead of a JSON file.

At each checkpoint and at the end of every turn print `run-state.mjs status --repo <main> --run <id>`: one read-only Markdown table of items/owners/next actions, handoffs, gates, rounds/caps and deferrals. Use this table for the status block above. Do not omit failed or parked records. `state.json` owns these structured facts; the ledger holds narrative and evidence. Audit malformed records and incomplete ownership with `run-state.mjs audit` (exit 0 clean, 1 not-ok, 3 error). Missing optional fields in legacy runs add no obligations.

Both `finish` and passing `learnings` refuse open|blocked items and sent|running|failed handoffs. A failed handoff remains owed unless a replacement is recorded or its linked item is parked with reason and next owner; history remains listed. Passing or recording another gate never erases owed work. No gate pass rule, review/fix cap or vendor rule changes: one full review plus a conditional same-reviewer delta, cap 2, vendors from the profile.

While work is owed, the allowed endings are: waiting on registered workers/jobs with items listed (job survivor/wait and Windows restrictions above still bind); a blocking owner card after own jobs settle; a resumable HANDOVER-NEXT.md with depth<=5 carrying open items by ID; or terminal `run-state.mjs park --reason <reason>`. A terminal parked run cannot finish or be accepted as passed. A milestone summary or a promised next step is not a turn-ending reason. The table lists the obligations and the allowed wait/stop reason; do not end with unregistered own jobs or missing files.

Discipline writes (`scope`, `defer`, `item`, `handoff`) on a finished run refuse with RUN_FINISHED. A terminal park report includes open|blocked items and every owed handoff, with original records and IDs preserved. Status gives finished precedence over any status field.
