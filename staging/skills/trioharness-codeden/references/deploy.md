# Azure ZIP deploy

Loaded when a task includes deployment. Binding when triggered.

- Deploy only with `node "<skill>/scripts/deploy.mjs" --target <name> [--sha <full-sha>] [--repo <repo>]`. Never hand-run `az` deploy commands, and **never deploy through CI pipelines**: no GitHub Actions workflow dispatch, no workflow or GitHub environment edits, even when such workflows exist. Never add repo-specific logic to the script: every repo specific lives in `<repo>/.trioharness/deploy.json`.
- Target types: `webapp` (App Service; builds locally, ZIP-deploys; template `templates/repo/deploy.json`) and `containerapp` (Container Apps; `az acr build` from a `git archive` extract of the SHA, so no local Docker, then `az containerapp update --image <registry>/<image>@sha256:<digest>` (digest-pinned, see below); template `templates/repo/deploy.containerapp.json`).
- No `deploy.json` → the script refuses; stop the run at "PR open" and mark deploy and browser test pending. Creating `deploy.json` is its own task: discover candidates read-only and **by name only** (`az containerapp list --query '[].{name:name,rg:resourceGroup}' -o table`, `az webapp list --query '[].{name:name,rg:resourceGroup}' -o table`, `az acr list --query '[].name' -o tsv`, the repo's Dockerfiles and build commands, the health or build-info endpoint); never run a bare `az … show` or paste its output anywhere — app environment values are secrets, propose the file, and have the user confirm every target before it is committed. Never guess targets or put secrets in it; authentication is the user's `az login` (needs AcrPush on the registry and Contributor on the app) or a QA-scoped service principal.
- The app must report its running commit SHA as exactly 40 hexadecimal characters on the health endpoint (a shorter hexadecimal SHA refuses `HEALTH_SHA_NOT_FULL` before any build or switch) (JSON: `shaField` is the dot path; plain-text body: `shaField` is `"."`) (the build receives it as `{sha}` / `TRIO_BUILD_SHA`). If it does not, adding that is its own task before the first deploy. For `HEALTH_SHA_NOT_FULL`, first check whether the running build already exposes the full SHA at another endpoint or JSON field; if so, correct the health URL or `shaField` through a separately reviewed `deploy.json` change on the default branch, then retry. If the running build exposes only a short SHA and needs a code fix, stop for the owner to arrange a separately reviewed bootstrap migration before retrying: the current script has no short-SHA bypass, and `--allow-unreadable` does not bypass this refusal. Do not hand-run Azure deploy commands or dispatch CI to work around it.
- QA (`agentAllowed: true`): the Architect deploys under the standing authorization in the repo AGENTS.md, only after the `done` gate passed and the commit is pushed. Run `--dry-run` first, then deploy; the script builds at the SHA (containerapp: a `git archive` extract; webapp: a detached worktree), deploys, and waits until health reports that SHA. The script never removes the build directory or a worktree: it reports `buildDir`, and deleting it is the person's decision. Exit 2 `VERIFY_FAILED` → run `--rollback` for that target, then report. Container Apps roll back to the previous verified image recorded in the history (the first deploy records the image it replaced), App Services to the previous artifact.
- **Older short-SHA rollback targets.** A rollback to an old revision whose health endpoint still reports a short SHA can switch traffic, then refuse `ROLLBACK_VERIFY_FAILED` because verification requires the full 40-character SHA. That failed rollback appends no history entry; the traffic switch is not automatically undone. Check the serving revision and report the result to the owner before any further action. Plan the endpoint/bootstrap migration above before relying on such an old revision as a rollback target.
- **Build values that live on the app** (client ids, tenant ids, non-secret frontend settings) are declared as `build.buildArgsFromApp: {BUILD_ARG: APP_ENV_VAR}` and read from the running target at deploy time — never stored in `deploy.json`, and shown in dry runs only as `<from app env VAR>`. A value the app holds as a secret reference is refused: build arguments must be non-secret.
- **Promotion, not rebuild:** a target with `promoteFrom: "<target>"` (or `--promote-from <target>`) deploys the exact image already verified there. The script refuses unless that target has a verified deploy of this SHA in its history and is currently serving it; production therefore runs the same bytes tested on QA. Since D2 it promotes by digest and proves the bytes (next bullet).
- **Digest pinning (D2).** The tag `<image>:<sha>` is mutable, so it is never the deploy reference. `az acr build` runs with `--output json`; `deploy.mjs` takes `runId` and the image digest from that build's own run record (`status` `Succeeded`, exactly one `outputImages` entry whose registry, repository and tag equal the login server, the image and the SHA) and updates the app with `<registry>/<image>@sha256:<digest>`. The tag is never read back as provenance. A missing, failed, ambiguous or digest-less record refuses `ACR_RUN_UNREADABLE` before any `containerapp update` (the build directory is kept). The history entry records `runId`, `sha`, `digest`, `image` (the pinned reference), `imageTag` (the tag reference) and `revision`. After the update and before any traffic call, the new revision's configured image must equal the pinned reference, otherwise `REVISION_IMAGE_MISMATCH` and traffic stays on the previous revision. A promotion (dry runs included) additionally requires that the verified source entry has a digest (`PROMOTE_SOURCE_NO_DIGEST`: an entry written before digest pinning must be redeployed on the source through this script first) and that the source's traffic is pinned (the same single-named-revision rule, `TRAFFIC_NOT_PINNED` for split, latest-revision or unreadable traffic), that its serving revision equals the entry's `revision` and that revision's configured image equals the entry's pinned image (`PROMOTE_SOURCE_DIGEST_MISMATCH`); both are checked before any destination change, and the dry-run plan shows `promotedRevision`, `promotedDigest` and `promotedRunId`. Rollback by digest is not part of this change.
- **Container Apps and traffic:** a target that pins traffic to one revision keeps serving the old revision after an image update. Since D2 the script enforces that precondition itself on forward deploys and promotions, read-only and fail closed, before any `containerapp update` on the destination (a `--rollback` does not run this preflight): `APP_SHAPE_UNSAFE` unless the app is in `Multiple` revisions mode with exactly one container (the one named by `container`, when set), and `TRAFFIC_NOT_PINNED` unless traffic is 100% on exactly one explicitly named revision (zero-weight extra entries are allowed; split, latest-revision or unreadable traffic is refused). It never changes a setting to satisfy these checks; a refusal means the app is fixed by its owner, not by the script. Given that, `deploy.mjs` creates the revision with a SHA-derived suffix, keeps the old revision serving, verifies the new revision on its own hostname while it holds 0% traffic, and only then appends an exclusive history intent record (`intent: true`, `verified: false`, with the SHA, revision, previous revision and image provenance) before switching traffic and verifying again. If the switch crashes, the intent supplies the previous revision for rollback; it cannot authorize promotion. A later entry for the same revision supersedes the intent in the in-memory ten-entry window; both files stay on disk. A failed canary means traffic never moved and there is nothing to roll back. It records the previously serving revision before touching anything, so `--rollback` is an instant traffic switch rather than a rebuild; a deploy with no recorded serving revision is refused, and a rollback is only accepted once the expected revision is confirmed to be the one serving. **Source shape (promotion):** the same `APP_SHAPE_UNSAFE` rule is applied to the source app, read-only, before the source's traffic, serving revision or configured image is read or accepted and before the dry-run plan is returned, so a Single-mode, multi-container, differently named-container or unreadable source is refused with nothing changed on the destination.
- **Stage at 0% and switch traffic (opt-in).** `--stage-only` creates a Container Apps revision at 0% traffic, verifies it on its own hostname and compares traffic weights before and after staging. `STAGE_TRAFFIC_CHANGED` includes a restore command. A successful stage records `staged: true` in history, skips cleanup and uses the separate authorization phrase `<app>:stage:<sha12>` when required. For webapps, staging deploys to a configured non-production slot and refuses with `STAGE_NEEDS_SLOT` otherwise. The result prints a promote command, `--switch-traffic <revision|slot> [--percent 1..100]`, which refuses unknown destinations with `UNKNOWN_REVISION` or `UNKNOWN_SLOT` and requires matching verified history and a full destination SHA (`UNVERIFIED_DESTINATION`). The switch phrase is `<app>:switch:<destination>:<percent>` when required (100 by default). A partial switch leaves the remainder on the heaviest other revision. A webapp swap uses the production target's policy and requires a full running production SHA for rollback. It records the switch in both histories and refuses `--percent` with `PERCENT_UNSUPPORTED`. The switch prints a rollback command and returns its authorization phrase separately when required. Combining stage, switch or rollback modes raises `DEPLOY_MODE_CONFLICT`, and an invalid percentage raises `PERCENT_INVALID`. Every existing gate still applies. A switch does not trigger the issue's `deployed-prod` transition, and cleanup keeps staged revisions that never receive traffic as `retirement-unproven`.
- **Opt-in revision cleanup (containerapp only).** Set `"revisionCleanup":{"quietDays":7,"keepPrevious":2}` in the target: quietDays is required (integer 1–365), keepPrevious defaults to 2 (integer 1–10); no other keys. Absent means no new calls or plan/history fields. Cleanup runs only after verified forward deployment, before its final append, and records `cleanup` in that entry and the result. Verified deployment still exits **0** when cleanup refuses, fails or skips; stderr reports the code. Calls time out after 120 seconds, total cleanup after 15 minutes; termination before the final append leaves the intent.
  - Only active, unlabelled, zero-traffic revisions old enough both since creation and proven retirement are deactivated. Retirement uses full history: the latest verified forward transition away establishes evidence; any later entry naming it as its own revision (verified, rollback, intent or failed) makes retirement unproven until a newer verified forward retirement supplies evidence. Later mentions only as previousRevision extend the cutoff to their latest time without restoring invalidated evidence. Invalid/future times remain unproven; an intent/failed entry alone establishes no evidence. An unnamed revision created before the oldest valid, verified forward history entry may use that entry's time (pre-history); newer unknown revisions are unproven. Kept reasons: `serving`, `previous` (K distinct recent previous holders plus the in-flight holder), `latest`, `labelled`, `traffic`, `recorded-target` (every identity in the newest ten entries), `young-created`, `young-retired`, `retirement-unproven`, `already-inactive`. Post-preview additions are `not-in-authorized-list`; unattempted names after a failure are `not-attempted`; candidates retained on a refused revalidation are `revalidation-refused`.
  - Dry-run and authorization show the names. With `agentAllowed:"with-authorization"`, the phrase is `<app>:<sha12>:cleanup-<h8>`, hashing canonical target/app/config/sorted names; every invocation recomputes it before authorization. Cleanup is restricted to preview ∩ fresh candidates. Unavailable preview accepts the legacy `<app>:<sha12>` phrase and skips cleanup. Traffic, labels, inventory, history and limit are revalidated immediately before mutation. Ambiguity refuses `REVISION_CLEANUP_REFUSED:<reason>`; `maxInactiveRevisions` must be explicitly readable as a nonnegative integer or cleanup refuses `REVISION_CLEANUP_REFUSED:maxInactiveRevisions`; purge simulation includes all creation-time ties and protects recorded rollback identities against `maxInactiveRevisions` purge (`REVISION_CLEANUP_WOULD_PURGE_ROLLBACK_TARGET`). Other outcomes: `REVISION_CLEANUP_FAILED`, `REVISION_CLEANUP_PREVIEW_UNAVAILABLE`. A failed deactivation stops the remaining attempts.
  - With the key set, rollback checks the revision identity's own forward SHA (legacy history without a verified field is accepted; explicit verified:false and intents are excluded), activates an inactive target, waits for active/Provisioned (scale-to-zero is allowed), then checks its hostname before changing traffic. Missing targets refuse `ROLLBACK_TARGET_PURGED`; unknown SHA on any target refuses `ROLLBACK_TARGET_UNVERIFIED` before authorization or mutation, and rollback dry-run includes `willRefuse: "ROLLBACK_TARGET_UNVERIFIED"` only when the key is set and the SHA is unknown. Unreadable state or failed health also refuses `ROLLBACK_TARGET_UNVERIFIED`. New az calls capture both streams without echoing bodies or failure output.
  - **Accepted consequence:** quiet time proves nothing about open requests/streams, direct callers or unique in-memory state. Opting in accepts interrupting those on superseded revisions older than quietDays. Azure may purge old inactive revisions at `maxInactiveRevisions`. No cross-process lock exists: revalidation narrows but cannot close the race; concurrent deploys/rollbacks on one app are out of scope.
- **What the evidence covers.** The decisions of the digest-pinned flow (run-record parsing, the pinned update arguments, the source-history association, the revision-image equality check and the history entry) are small exported functions that `main` itself calls, so they can be checked on their own with synthetic values; the shape and traffic refusals are likewise pure checks. That is not a run of the whole flow. The ordering of `main`'s steps, history persistence, the real `az` serialization and Azure's actual traffic routing are verified only by a live deploy through this script; until a QA deploy has recorded the build run, SHA, digest, pinned image, revision and history, and the production revision and image have been compared with that record, treat "the same bytes run in production" as designed, not proven. The deploy tests under `scripts/deploy-guard.test.mjs` are written as regressions; whether they have been run is stated by whoever reports on them.
- **Append-only history and create-only artifacts (H3).** The script never rewrites, truncates, replaces or removes a history or build file. History and new ZIPs live in `~/.trioharness-lean/app-history/<app-slug>-<identity-hash>/` (see the app-history rule below). The legacy `<artifacts>/history.json` and `history.d/` under `~/.trioharness-lean/artifacts/<repo>/<target>/` are read only: their bytes are unchanged by any run. A container-app forward deploy or promotion appends an intent file before switching traffic and a final result file after health verification; a webapp forward deploy or a successful rollback appends one file. Each append creates a new `history.d/<NNNNNN>.json` in the app store (six digits, numeric order, gaps allowed), holding a JSON array with exactly one entry object, opened exclusively and written with one write call (a short write refuses `HISTORY_ENTRY_UNREADABLE`; the file is retained as written, never rewritten or removed). Within a directory the history is the legacy array followed by those files in numeric order; the app view follows the migration rules below; every file stays on disk, and rollback selection and the promotion source look at the last ten entries in memory only. Nothing creates `history.d` until the append itself: reading, `--dry-run` and the preflight refusals leave no history storage (the artifacts directory, the build directory, the source export and the ZIP of a run that fails later are kept as evidence and reported). A name in `history.d` that is not `NNNNNN.json`, or an entry file that is empty, incomplete or not a one-element array holding an entry object, refuses `HISTORY_ENTRY_UNREADABLE` naming the path before anything is changed; the script never skips, repairs or removes it. A number collision (another run appended at the same moment) is retried with the next number at most 20 times and then refuses `HISTORY_WRITE_CONFLICT`, as does a next number above 999999; other I/O errors are not retried. Exclusive creation prevents overwriting but does not publish a complete file atomically or serialize two deploys: a reader can meet an entry that is still being written and refuse, and number order need not equal the order in which deploys finished on Azure. A webapp ZIP is written create-only to `<sha>.zip`, or `<sha>.2.zip`, `<sha>.3.zip` and so on if that name exists (at most 50 names, then `ARTIFACT_WRITE_CONFLICT`), and the forward history entry records the absolute `artifact` path actually written. A webapp rollback redeploys that recorded path and refuses `ROLLBACK_ARTIFACT_MISSING` if that exact file is missing, with no fallback to another file; only an older entry without an `artifact` field uses `<sha>.zip`. Entries the older script already truncated, and ZIPs it already overwrote, cannot be restored.
- **No `git fetch` inside the script (H3): run it yourself first.** `deploy.mjs` never fetches. Before a deploy, dry run or rollback, the person runs `git fetch <remote>` in the repository, outside the script. The script then reads `git ls-remote --heads --refs <remote>` and compares each branch it relies on with the local `refs/remotes/<remote>/<branch>` tip (exact refs; the symbolic `<remote>/HEAD` alias is ignored): first the config-source ref, before `deploy.json` is trusted, and then, after the config is loaded, the effective remote and default branch (`remote` and `defaultBranch` from the config, even when they equal the first ones), before any SHA is selected or a rollback is planned. A branch whose local tip differs from, or is missing against, the advertised tip refuses `REMOTE_REF_STALE`, naming both tips: run `git fetch <remote>` and retry; nothing was changed. A failed `ls-remote`, a malformed or empty advertisement, or a missing advertised head refuses `REMOTE_REF_UNREADABLE`. "Is the SHA on a remote branch" counts only branches that are fresh in this sense. The running-commit, ancestry and overwrite checks above are unchanged and still read local objects; the freshness check is an added gate, not a replacement for any of them. This is an operational change from earlier versions, which fetched themselves. Not covered by these statements: `ls-remote` and `git worktree add` (webapp builds) run native Git, which may update `known_hosts` or a credential store and have its own failure handling, hooks and configuration; the configured build command and the `az` CLI write wherever they write. Those effects are not audited here.
- **Never route around the script.** If `deploy.mjs` refuses (agent process, non-interactive terminal, SHA not on the default branch, prerequisite target on a different SHA), that is the gate doing its job: prepare the exact command and stop. Running `az containerapp update`, `az containerapp ingress traffic set`, `az webapp deploy` or a CI workflow by hand is forbidden, and a chat authorization does not replace the check — to let agents deploy a target, the user changes `agentAllowed` in `deploy.json`, which is a recorded decision.
- **Three authorization modes per target.** `agentAllowed: true` — the Architect deploys under the repo's standing authorization (QA). `agentAllowed: "with-authorization"` — the Architect may deploy, but only after asking the user for that one deploy: it computes the phrase `<app>:<sha12>`, asks the user to reply with exactly that, and passes it as `--authorize`; a wrong or missing phrase is refused, and every other gate (default branch, promotion source serving the same SHA, canary) still applies. A **rollback** on such a target needs its own phrase `<app>:rollback:<revision or sha12>` passed as `--authorize` (the deploy phrase is not accepted); `--rollback --dry-run` prints it as `authorizationPhrase` without requiring it. `agentAllowed: false` — the user only, at an interactive terminal. Changing the mode is a `deploy.json` edit, reviewed like code; the phrase never substitutes for it.
- Production (`agentAllowed: false`): the script refuses agent processes and non-interactive terminals and requires the SHA on the default branch and the same SHA running on QA. The Architect only prepares the exact command for the user.
- The script never runs database migrations and rejects build steps that would. Migrations follow `references/promotion-and-db.md`.
- Record the deployed SHA, target and health result in the run ledger and run-state (`deploy-qa`).
- **Never replace running code that is not in the SHA you deploy (2.31).** Before deploying, the script reads what the target runs. If that commit is not an ancestor of the SHA being deployed (an unmerged branch, a hotfix, a build from a deleted branch) it refuses with `WOULD_OVERWRITE_UNMERGED` (or `found in no branch of this repository`), dry runs included. Only a person may override with `--allow-overwrite <first 12 characters of the running SHA>`. An agent additionally needs the user's recorded answer "accept replacing it" from the gate-0b card for that exact target and commit (`--run <id> --ledger <main checkout>`); otherwise `OVERWRITE_NOT_AUTHORIZED`. The normal fix is to bring that code into the repository first (merge or promote it) in its own task.
- **Deploy guards (2.35): what protects live code, and what does not.**
  1. `deploy.mjs` reads `.trioharness/deploy.json` from the **default branch** (what `origin/HEAD` points at), never from the branch being deployed or the working tree. A new target, or a switch of `agentAllowed`, counts only once it is merged. A target that exists only locally is `UNKNOWN_TARGET`; a default branch without the file is `NO_DEPLOY_CONFIG_ON_DEFAULT`. A person bootstrapping a repo may pass `--config-from-worktree`; an agent may not.
  2. It stops with `RUNNING_REF_UNREADABLE` when the target's health endpoint cannot be read or reports no commit SHA (three attempts first, to absorb a restart). Without a readable running commit the overwrite check above cannot run, so the script cannot prove it will not replace unmerged code. An agent stops and asks the user through a card; a person may deploy with `--allow-unreadable <target>` (the first deploy of a build that starts reporting its commit, or an endpoint blocked by an IP restriction). Typical causes: an older build without the commit endpoint, an access restriction answering 403, the app being down.
  3. For deploys that run in GitHub Actions, copy `templates/repo/github/pre-deploy-ancestor-check.sh` into the repo and run it before the deploy step (it stops unless the running commit is an ancestor of the commit being deployed), and use a GitHub environment limited to the default branch with a required reviewer (`templates/repo/github/deploy-guard.example.yml`). Environment rules are repository settings: changed only by the owner, through a card.
  4. Honest limit: nothing here stops a person with Azure rights from running `az` by hand, or a workflow dispatched from a branch the environment rules do not cover. That path is closed only by agents never doing it (this reference) and by the owner's approval cards.


## App history follows the Azure app

The rule is one local history per Azure app identity, shared across checkout folder names and deploy target names. The identity is the JSON array `[type || "webapp", subscription, resourceGroup, app, slot || ""]`, with every value trimmed and lowercased. Its SHA-256 prefix (16 hex digits) and a safe app-name slug name the directory `~/.trioharness-lean/app-history/<app-slug>-<identity-hash>/`. New ZIPs live there too. The first append creates `identity.json` exclusively; a partial, different or unreadable existing identity refuses `HISTORY_IDENTITY_MISMATCH`. A failed identity write is retained, and the script never repairs or replaces that file automatically. Every new history entry, including imported entries, records `appIdentity`, the directory key. Promotion reads the source target's app store through the same loader. The H3 entry format, create-only writes and ten-entry selection window remain unchanged.

The script migrates attributable legacy history itself, without hand copying, deleting anything or opening legacy files for writing. It checks its own former `artifacts/<checkout-basename>/<target>/` directory and, for Container Apps, the other two-level directories under `artifacts/`. The own directory is trusted unless a recorded string revision belongs to a different app: that own source is ambiguous (`foreign-app-own-dir`), is not imported, and makes revision cleanup refuse `REVISION_CLEANUP_REFUSED:history-ambiguous`. Null, undefined and non-string `revision` values are ignored (including the nulls emitted for webapps and image rollbacks). A string revision belongs to this app exactly when splitting it on `--` yields two parts and the first equals the app name case insensitively; Azure names such as `<app>--x1y2z3a` count, not just script-generated suffixes. Every other string revision is foreign. Another directory needs at least one this-app revision; a foreign string revision silently excludes that other source, and no positive revision evidence makes another directory ineligible. The own legacy directory is read strictly: malformed or unreadable history refuses `HISTORY_ENTRY_UNREADABLE` before anything changes. Only other folders use lenient evidence collection, and an unreadable positively attributed source is ambiguous and never imported. Every present SHA must resolve to a commit in this repository, including own-directory history and webapp history. If another target in the governing default-branch config names the same type and app but a different subscription, resource group or slot, OTHER-folder legacy sources of that app name are ambiguous and are not imported; the own source retains its historical trust. The other-folder ambiguity persists on every run while both conflicting targets remain listed, even after an own-source import. The person's existing `--config-from-worktree` bootstrap exception still uses its explicitly selected config.

A read or dry run creates no files or directories. Its virtual view is the store in append order, followed by eligible pending imports. Nothing sorts that read view. Before any merge, each source must itself be non-decreasing in valid `at` timestamps. A backwards source is ambiguous and blocks the pending migration batch; sorting never rescues its causal order. When multiple sources contribute, entries without valid `at` also make their source ambiguous. Only individually valid sources can merge by time into an initially empty store; a single source keeps its own order. With an existing store, a new source or tail must have valid timestamps at or after the store's last valid timestamp; older or invalid tails are ambiguous. Once any entry has `migratedFrom`, valid timestamps in view order must be non-decreasing; a backward timestamp makes the history ambiguous without rearranging it.

Pending entries are persisted immediately before the run's first history append, using the same complete one-record H3 writer. Each has `migratedFrom: {dir: "<folder>/<target>", index: <zero-based index>, hash: "<sha256>"}`. The hash covers canonical JSON of the original source entry, recursively sorting object keys and preserving array order, before artifact-path recovery. An existing pair is skipped only when its hash matches; a changed or missing hash makes that source ambiguous. Identical entry content already attributed to another source makes the later source ambiguous, so hand-copied history is never imported twice. Interrupted imports still resume and attributable later tails can be picked up. If the own legacy folder is deleted, emptied or changed after import, history is flagged `source-changed` and `revisionCleanup` keeps refusing `REVISION_CLEANUP_REFUSED:history-ambiguous`; nothing is repaired automatically and the owner decides through a card. Each imported source logs `DEPLOY: history: imported N entries from <dir>` to stderr. Each ambiguous source emits `DEPLOY: history: <dir> not imported (<reason>)`, once per source/reason in a run, including dry runs. A legacy webapp entry missing `artifact` gets the absolute `<legacy-dir>/<sha>.zip` path if that ZIP exists. Rollback continues to use the recorded absolute path. A partial or short store entry refuses `HISTORY_ENTRY_UNREADABLE`; it is never repaired or skipped.

For other folders, positive revision evidence with unreadable records or conflicting config identities is ambiguous. An unknown commit, changed source hash, duplicate source content, or unsafe migration chronology is also ambiguous; unreadable own history instead refuses strictly as described above. Nothing ambiguous is imported. Revision cleanup then refuses `REVISION_CLEANUP_REFUSED:history-ambiguous` in both preview and execution, without deactivation; a verified deploy can still succeed and record the cleanup refusal. Rollback with cleanup still refuses `ROLLBACK_TARGET_UNVERIFIED` if its forward SHA is absent from the merged view. Other gates, authorization phrases, retention thresholds and refusal rules remain in force. Targets without revision cleanup use the same app store and migration loader, with their existing deploy and rollback behavior.

Limits: history is local to this machine and user home; another machine or home has separate history. A subscription name and its GUID produce separate keys. Legacy records cannot distinguish a same-named app in another subscription/resource group that the current config does not list. Repointing a target within the same folder makes cleanup refuse `history-ambiguous` when its own legacy history contains a string revision belonging to another app. Webapp history has no revision evidence, so only the own legacy directory is imported; repointing a webapp target to another app of the same repo retains its old own-directory entries, as before. A legacy tail is usable only when attributable and chronologically safe. Earlier truncated history or overwritten ZIPs cannot be recovered. No cross-process lock is added: exclusive file creation prevents overwrites but does not serialize deploys, rollbacks or migration; simultaneous app operations remain out of scope. These local tests do not prove Azure behavior.
