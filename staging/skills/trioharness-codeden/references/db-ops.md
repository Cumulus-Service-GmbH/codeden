# db-ops: reaching the databases, services and the Linux server the Azure apps use, from the Mac

Some SQL servers and the Linux server (`erpure-linux`) are not reachable from the Mac directly: they accept connections only from the Azure network the apps run in. The Mac therefore does **not** connect itself. It asks a small helper that runs inside that network, through the `dbops` command. Nothing here needs the Windows machine, a VPN or a new open port.

## Is it installed?
`~/.trioharness/db-ops/dbops --help` exists on the Mac that was set up for it. If the file is missing, db-ops is not set up on this machine: say so in the task card and ask the user (card) — never improvise a tunnel, a firewall rule, a VPN, or a direct connection from the Mac. **`dbops --help` is the contract**: use only the commands it lists; if it differs from this page, trust `--help` and report the difference in the final report.

## What it does (commands as installed)
- `dbops probe <app>` — read-only: can the helper reach that app's databases? Prints names and OK/failed, never connection strings.
- `dbops query <server-port-or-alias> <database> "<SELECT …>"` — read-only login. A statement that writes is refused by the wrapper (exit 4). Results are small row sets; never dump a table into chat, a packet or a ledger. Customer databases are out of scope and are refused unless the repo lists them as app-path systems (below).
- `dbops migrate <app> <database> --script <file.sql> --plan` prints what would run; then `--confirm-staging` runs it on a non-production database, or `--confirm-prd <sha256-of-the-script>` on production. **A production migration is the user's**: the Architect prepares the script, the plan and the sha256, then asks a card; it never passes `--confirm-prd` without that card's answer (see `references/promotion-and-db.md`).
- `dbops audit` — every call is logged (who, when, database, statement hash); read it when reporting what was done.
- Linux server: only through the restricted relay `dbops` offers (when `--help` lists it): named, allow-listed actions through the Azure Arc connection. Anything as root is a card first, naming the exact command. The server is live (document conversion and the web front end the chat apps use): no restart, package change or config edit without a card.

## Connection strings
The Architect does not look for them, copy them or ask for them. The helper reads the app's connection string from Azure Key Vault or the app's own settings **inside Azure** and uses it there. If an app has no usable string, the card asks the user to paste it once in the masked dialog (`secrets.mjs set --name <NAME>`), never in chat.

## App-path access, with a person in the loop
What the repo's Azure app can reach, an agent may reach too, through the same network path (VNet integration, Hybrid Connection, private endpoint) and always with the user in the loop. This covers the app's SQL servers, databases behind its Hybrid Connections (including a customer's ERP database) and APIs such as the SAP Business One Service Layer. It replaces the blanket "customer databases are out of scope" only for systems the repo opts in to.
- **Opt-in, per system.** A system is in scope only when the repo's AGENTS.md lists it under *App-path systems* (name, kind, environment, owner; never a host secret or connection string). That list is changed only by a pull request the user approves (AGENTS.md is a high-risk path). A system not listed stays out of scope and is refused.
- **Reads.** The first read of a listed system is a card naming the system, the environment and the read-only identity; the user's answer is recorded as a standing order for reads on that system only (`standing-orders.mjs add --topic apppath-read-<system>`), and the user can revoke it. Standing orders never cover production, so reads on a production system are approved by one card per run. Reads are SQL `SELECT` and Service Layer `GET` through an identity that cannot write; small row sets only, as for `query` above.
- **Writes, one card each.** Every write is the user's decision, every time: SQL DML or DDL, a migration, a Service Layer `POST`/`PATCH`/`PUT`/`DELETE` or action, a file or job on the far side. The card shows the target system and environment, the exact statement or request (or the script) with its sha256, the expected effect and the rollback. The agent runs exactly what the card showed, once, then records the result; a changed script is a new card. The app normally does the writing: an agent write is the exception (a migration, a repair the user asked for), never a routine step.
- **No standing write rights.** Agents get a read-only identity by default. A write path stays disabled and is enabled only for the window the card approved (or the helper requires a per-call confirmation such as `--confirm-prd <sha256>`); a permanently enabled write login is a finding to report.
- **The app's own credentials and settings are not the agent's.** The helper or a separate agent gateway holds what it needs inside Azure; the agent never reads the app's connection strings, Key Vault values or relay keys, never reuses the app's SAP user (an extra session can log the app out), and never changes the app, its settings, its Hybrid Connections, firewall or DNS, nor restarts it.
- **Customer systems.** The card also asks the user to confirm the customer agreed to agent access; without that answer, nothing is sent.
- **Setting the path up.** If `dbops --help` offers no command for a listed system, the agent does not improvise one: it writes a setup proposal (resources, identity, read-only by default, why it cannot affect the live app, rollback) and every Azure step is a card. Autopilot never answers these cards: a question about app-path access, a Service Layer or a database write is always a gate.

## Rules
- Reads first, writes only through `migrate` or an app-path write card. Never run `sa`/`sysadmin` style logins from the Mac, never create logins, never widen a firewall rule.
- Output that carries values (connection strings, tokens, personal data) is not pasted anywhere; run `guard.mjs --scan` on any file made from db output before it is read by another agent or sent.
- Record every `dbops` call (command, database, exit status) in the run ledger; a failed probe is a finding, not a reason to try another route.
